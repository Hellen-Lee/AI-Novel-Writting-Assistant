## 0. 总体链路与阶段划分

```
前端选择/粘贴/拖拽
   → 前端预校验（白名单 + 大小）                    [B]
   → POST 上传到后端 → 落盘 + 解析 → 返回附件记录    [A][C][D]
   → 附件 chip 展示在输入框工作区（可移除）           [B]
   → 发送：GenerateRequest 携带附件 ID + 选中文本     [E]
   → 生成服务组装 prompt（附件材料块 / 多模态消息）    [E]
   → user 消息持久化（绑定 session_id + message_id）  [F]
   → 页面刷新后历史消息回显附件                       [F]
   → 删除会话 → 级联清理附件目录                      [G]
   → 全程边界与异常处理                               [H]
```

- 解析库：pypdf，提取文本层。
- **扫描版 PDF**（提取结果近乎为空）→ 不算 failed，返回 `text=""` + `parsed.note="扫描版PDF，无文本层"`，发送时占位提示用户；P2 再考虑 OCR。

- `text_truncated=true` 时，气泡附件 chip 的 title 应提示「内容已截断」。

> **实现记录（260913）**：`attachment_parser.MAX_TEXT_CHARS = 8000` 模块常量（后续配置化改这里）；`text` 存截断后文本、`chars` 存原始字符数、`text_truncated` 标记齐全；chip title 提示属前端 B 阶段接线。

### D7. 明确不支持的格式与话术（P0）

## E. 发送方案（P0，依赖 A1 / B / C / D / F1）

### E1. GenerateRequest 扩展（P0，依赖 A1）

- 新增字段 `attachments: list[str]`——**只传附件 ID 列表**，不重传内容：解析产物以落盘为准，避免大 payload、防止前端篡改内容与已解析产物不一致。
- 新增字段 `selection`（或复用现有 `selected_text`）：工作区第二行的选中文本继续走现有 `$selected_text` 注入通道，**不并入附件**。
- 前端 `buildAttachmentPayload` TODO 按此实现：返回 `{ attachments: [att_id...], selected_text }`。

### E2. 消息与附件的对应关系（P0，依赖 E1）

- 对应关系为「**一条 user 消息 ↔ 一组附件**」：附件绑定在 user 消息上（持久化见 F1），assistant 消息不携带附件。
- 附件 + 选中文本 + 文本输入三者相互独立、可任意组合为空：只有附件没有文字时 user_input 兜底为「（基于附件/素材）」（沿用现有空输入兜底思路，文案可再定）。
- 多轮对话中，历史轮次里的附件仅以「名称 + 类型」出现在摘要（summary）里，不再重复注入全文（防止 context 暴涨）；最近 N 轮内的附件全文按正常注入。

### E3. prompt 组装规则（P0，依赖 D 的产物）

- 文件附件：在 user 消息前拼接独立的「附件材料块」，约定结构（伪格式，实现时定稿）：
  - `【附件·文件】{name}\n{text}`（text 已截断，块尾注明截断情况）
  - 多个文件按上传顺序依次拼接，块与块之间分隔。
- 引入 prompt 变量 `$attachments`（材料块整体文本），注入方式对齐 `prompt_builder` 现有 `$变量` 机制：`quick_action` 与 `skill` 两类 SKILL.md 均可引用；未引用变量时，材料块兜底拼在 user 消息头部（**不允许附件内容被静默丢弃**）。
- 受 `context_budget` 约束：材料块参与总预算，超预算时从**最早的附件**开始降级为「仅保留名称 + 截断提示」（并把降级事实写入 run step，供观测）。
- 图片附件（依赖 C2 的能力标记）：
  - 支持 vision：按 OpenAI 兼容多模态格式发送（data URI base64，本地服务无外网上传）；优先发缩略图还是原图 → **发压缩后的图**（C3）。
  - 不支持 vision：占位文本 `【附件·图片】{name}（当前模型不支持识图，已跳过）`。
- 技能引用（B4）：映射到现有 `skill_name` 显式调用路径；与附件同发时材料块照常注入，二者不冲突。

### E4. 发送时机与失败边界（P0，依赖 H）

- 发送前前端校验：工作区内存在 `failed` 状态附件时**阻止发送**并提示（或允许剔除失败项后发送，实现时二选一，倾向后者更顺手）。
- 上传请求进行中（未拿到 att_id）不允许发送该附件：按钮置灰或自动等待。
- 生成开始后清空工作区（沿用现有清空行为），但历史消息立即回显附件（依赖 F1/F2）。

### F1. user 消息绑定附件（P0，依赖 E2）

- `session_store.make_message` 扩展（或 `append_messages` 侧组装）：user 消息新增
  - `attachments`: `[AttachmentRecord 完整摘要]`（含 id / type / name / size / status / parsed 摘要；文件 `text` ≤ 4k 时直接内嵌，超出仅存落盘引用，回显时按需拉取——**MVP 简化：text 一律不内嵌进会话 JSON，只存引用**，会话文件保持轻量）
  - `selection`: 选中文本（若本轮有）
- 落盘时机：沿用 `generation_service` 现有 `append_messages(user_msg, assistant_msg)` 单点，附件信息在构造 `user_msg` 时一并带上，**不新增第二次写盘**。
- `updated_at` / 索引刷新机制不变。

### F2. 引用关系登记（P0，依赖 F1）

- 新增 `attachment_store` 服务：负责附件落盘、按 id 查找、以及「已引用 / 孤儿」判定（扫描会话 JSON 中 `attachments[].id` 建立引用集合，带内存缓存，会话保存时失效）。
- A4 的删除接口、G 的级联清理均以它为准绳。

### F3. 历史消息回显（P0，依赖 F1 / A3）

- 现有 `GET /sessions/{sid}` 返回完整 messages → `MessageItem` 对 user 消息渲染 `AttachmentBundle`（组件已就绪）：`message.attachments` → 第一行 chip；`message.selection` → 第二行引用行；图片 `url` 指向 A3 thumb 接口 → **刷新后可看**。
- 回显数据必须来自会话 JSON，而非前端内存态。
- 失败附件（历史中 status=failed 的，理论上不应存在；若存在如发送被阻止前的残留）回显时显示失败态。

验收（本节合并）：上传 → 发送 → 刷新页面 → 附件 chip 与引用行完整重现；图片 hover 缩略图可用；会话 JSON 中消息体积可控（不含大文本）。

## G. 级联删除与生命周期管理（P0 最小实现，依赖 F2）

### G1. 删除会话级联清理（P0，依赖 F2）

- 改造 `session_store.delete_session`：删除 `sessions/{sid}.json` 与索引条目之后（或之前，顺序见 G2），删除 `agent/attachments/{sid}/` 整个目录。
- 目录不存在时静默跳过（兼容旧会话无附件）。

### G2. 删除顺序与半删防护（P0，依赖 G1）

- 顺序：**先删附件目录 → 再删会话 JSON**。理由：若中途崩溃，残留「无附件的会话」比残留「无会话的附件」（孤儿文件）危害更小，且孤儿文件可被 P2 清扫任务回收。
- 更稳妥的变体（P1）：先把附件目录改名为 `attachments/{sid}.trash`，删完会话 JSON 后再物理删除，崩溃重启时扫描 `.trash` 续删。

### G3. 未发送附件的清理策略（P1，依赖 A4 / F2）

- 用户主动移除：A4 接口实时删。
- 兜底清扫（P2）：会话加载或定时任务扫描 `attachments/` 下未被引用且 mtime 超过阈值（如 24h）的文件删除，防浏览器中途关闭留下的孤儿。
- 项目删除（`project_store` 既有逻辑）天然级联——附件在项目目录内，无需额外处理；在删除项目的文档/注释中标注这一事实。

### G4. 单条消息删除（P2，依赖 F2）

- 若未来支持删除历史消息：移除消息内 `attachments` 引用后，判定孤儿并删除对应文件。
- MVP 不做单条消息删除，此条仅登记以避免设计遗漏。

## H. 边界与异常（P0 最小集贯穿各阶段）

### H1. 格式白名单（P0，依赖 A1）

- 前端（B2）+ 后端（A2）双重校验：扩展名 + MIME 白名单；后端为准（前端可被绕过）。
- 注意扩展名伪造（如 `.jpg` 实为 exe）：图片用 Pillow 试开、文件按声明类型解析器解析，解析器内部异常统一 failed——**解析本身即二道防线**。

> **实现记录（260915）**：已完成。后端现在同时校验扩展名与 MIME 白名单，并与前端同步支持 `.bmp`；图片仍通过 Pillow 进行解析二道校验，伪造扩展名会在解析阶段失败。

### H2. 单文件大小上限（P0）

- 图片 ≤ 5MB；文件 ≤ 10MB（数值可配置，后端流式读取累计字节判断，超限即中断并返回 413 风格错误，不要整读进内存）。

> **实现记录（260915）**：已完成。前端预校验与后端流式落盘均执行图片 5MB、文件 10MB 上限，超限文件不会保留半成品。

### H3. 数量与频率限制（P0/P1）

- 单条消息附件数 ≤ 5（与设计稿「5 个附件」的心智一致）；P1：并发上传请求排队，避免一次选 20 个文件打爆本地服务。

> **实现记录（260915）**：已完成。前端限制单轮最多 5 个附件，后端对单批超过 5 个直接拒绝；前端连续选择/粘贴产生的上传请求通过串行队列执行，并预占队列中的附件名额，避免并发写入与绕过数量上限。

### H4. 解析失败的 UI 与发送策略（P0，依赖 C/D）

- 失败 chip：保留在工作区、显示失败标识与原因（title / 红点），用户可移除。
- 发送策略：剔除失败项后允许发送（E4 定稿）；**禁止**静默把失败附件当成功发送。

### H5. 会话状态异常（P0）

- 会话在生成中被删除：上传 404，前端提示「会话已删除」。
- 附件文件落盘后被外部删除（用户手动清理 data/ 目录）：A3 读取 404，前端回显降级为「文件缺失」占位 chip，不白屏。

### H6. 磁盘与编码（P1/P2）

- 中文文件名：存储名一律 `att_id.{ext}`，原始名仅存 record 中展示，规避编码/非法字符问题（Windows 平台路径约束）。
- P2：data 目录剩余空间检查（低于阈值拒绝上传），低优先级。
