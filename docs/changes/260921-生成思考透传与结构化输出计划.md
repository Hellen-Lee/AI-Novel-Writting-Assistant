## 0. 背景与现状

### 0.1 当前链路（两次模型调用）

```
用户点续写
  │
  ├─ ① 工具决策轮（0~3 轮，MAX_TOOL_ROUNDS=3）        ← 非流式 client.chat
  │    模型决定调不调工具；reasoning 全部消耗在这里
  │    content 被丢弃不展示（仅 tool_answer 兜底用）
  │
  ├─ ② 最终正文流                                      ← 流式 client.chat_stream
  │    纯 content 流式输出
  │
  └─ 定稿：_decide_draft → meta → 落盘 → 摘要 → save_run
```

### 0.2 关键发现（一切优化的前提）

`model_client._iter_chat_deltas`（`model_client.py:402`）解析 SSE delta 时**只取 `content` 与 `tool_calls`，`reasoning_content` 字段被整体丢弃**。对 deepseek-v4-flash 这类推理模型：

- 模型**已经在思考**，token 已经计费，但过程对用户完全不可见；
- ① 工具决策轮为非流式，用户在正文开流前有一段**完全黑盒的等待期**，且这往往是最长的一段。

### 0.3 优化方向总览与优先级

| 方向 | 一句话 | 优先级 | 状态 |
| --- | --- | --- | --- |
| **A** | 透传 ② 最终流的 `reasoning_content`（原生思考） | P0，最先做 | ✅ A1-A5 已完成 |
| **D** | ① 工具决策轮流式化，思考过程实时透出 | P0~P1，依赖 A | ⬜ 未开始 |
| **B** | Prompt 级 `<plan>` 结构化分析段（先分析后正文） | P1，D 验收后实施 | ⬜ 未开始 |
| **C** | 独立「构思」调用（两段式，节拍表可确认） | P2，远期 | ⬜ 未开始 |

**依赖关系**：`A → D → B → C`。D 复用 A 的 delta 解析与 SSE 帧；B 等 D 的工具决策轮流式化、回退和多轮工具行为稳定后再改变最终正文 prompt；C 是交互升级，需先验证「用户想看思路」和 plan/节拍价值后再上。

**总原则**：
1. 思考文本（无论来源）**一律不进会话历史 `messages[].content`**，不污染下一轮上下文、不重复计费；只进 run_store（Agent Viewer 可回看）。
2. 思考文本**不参与** `_decide_draft` 长度启发式、字数统计、锚哨兵解析、词数展示。
3. 非推理模型 / 不支持字段时，所有改动必须**零行为变化**（无字段 = 无帧 = 前端不渲染）。

## A. 透传最终流 reasoning_content（P0）

### A1. `model_client._iter_chat_deltas` 识别 reasoning 字段（P0，无依赖）✅ 260922

#### A1.0 各家官方文档调研结论（260921 联网核实）

| 厂商 / 模型 | 思考字段（流式 delta 内） | 出现顺序 | 备注 |
| --- | --- | --- | --- |
| **DeepSeek**（deepseek-reasoner / V4 系列 thinking mode） | `delta.reasoning_content` | 恒在 `content` 之前 | ✅ 已核实（api-docs.deepseek.com）。**工具调用时必须在后续请求把 `reasoning_content` 原样回传，否则 400** |
| **Kimi / Moonshot**（kimi-k2.6 / k2.7-code 等 thinking 模型） | `delta.reasoning_content` | 恒在 `content` 之前 | ✅ 已核实（platform.kimi.com）。多步工具循环内要保留 reasoning 回传；`thinking.keep` 控制跨轮保留；建议 max_tokens ≥ 16000 |
| **Qwen / DashScope**（Qwen3.5+ 混合思考模型，OpenAI 兼容模式） | `delta.reasoning_content` | 恒在 `content` 之前 | ✅ 已核实（help.aliyun.com / docs.qwencloud.com）。`enable_thinking` 开关；官方 FAQ 明示「function calling 时必须把 reasoning_content 放回后续 assistant 消息，否则降低准确性」 |
| **OpenAI**（o 系列 / GPT-5，Chat Completions） | **无字段，思考不暴露** | — | ✅ 已核实。思维链不可见，仅 Responses API 有 reasoning **摘要**项（`summary`，非原文）；走 chat/completions 的本项目架构拿不到，A 阶段对其零收益属预期 |
| **GLM / 智谱** | `delta.reasoning_content`（业内通行约定） | 预期同上 | ⚠️ 未核实：该条搜索结果被用户拒绝共享。实施时以 `https://docs.bigmodel.cn` 实测为准 |
| **Gemini** | 原生 API 用 `parts[].thought:true` 承载 thought summary；OpenAI 兼容层行为未核实 | — | ⚠️ 未核实：搜索结果被用户拒绝共享。本项目走 OpenAI 兼容端点，实施时实测该端点 delta 是否含 reasoning 字段 |

**结论**：国产主流推理模型（DeepSeek / Kimi / Qwen / 大概率 GLM）已收敛到同一约定——**delta 层 `reasoning_content`，且恒在 `content` 之前**。兼容实现只需认两个字段名（`reasoning_content` 优先、`reasoning` 兜底），无需按厂商分支。

#### A1.1 实现（P0）✅ 260922

- 在 delta 解析处（`model_client.py:436` 附近）增加：
  ```python
  reasoning = delta.get("reasoning_content") or delta.get("reasoning")
  if reasoning:
      yield {"type": "reasoning", "text": str(reasoning)}
  ```
- 两字段名的优先级即厂商兼容策略：`reasoning_content`（DeepSeek/Kimi/Qwen/GLM 约定）→ `reasoning`（部分网关/新格式兜底）。
- 依据「恒在 content 之前」的共识，前端可以假定 thinking 流先于正文流，但**实现不得依赖该顺序**（B 阶段的 plan 思考会穿插在正文流中，前端解析要按事件类型而非顺序驱动）。
- 非流式 `chat()` 的返回 message 暂不处理（①轮属于 D 阶段范畴）。

验收：用推理模型跑一次 `chat_stream`，能看到 `{"type":"reasoning"}` delta；非推理模型输出与现状逐字节一致。

### A2. `generation_service` 最终流转发 thinking 帧（P0，依赖 A1）✅ 260922

- `iter_generate` 最终流式循环（`generation_service.py:511` 附近）增加分支：
  ```python
  if delta.get("type") == "reasoning":
      yield _sse({"type": "thinking", "text": delta["text"]})
      continue   # 关键：不进 parts，不算正文
  ```
- SSE 新帧契约：
  ```
  data: {"type":"thinking","text":"..."}   # 增量；可能穿插在 content 之间（极少见）
  ```
- 更新 `09-Agent原生工具调用.md` §4 的 SSE 帧契约表。

验收：前端能看到 thinking 帧到达；`full` / `parts` 不含任何 reasoning 文本；`_decide_draft`、锚哨兵解析结果与改造前一致。

### A3. 思考文本持久化策略（P0，依赖 A2）✅ 260922

- 本次 turn 的完整 reasoning 文本累积到 run_store：`make_step("agent", extra={"reasoning": ...})`，Agent Viewer 可展开查看。
- **不**写入 `session_store` 消息（原则 0.3-1）。若后续需要刷新后回显思考（P1 可选），再增加 message 元字段 `thinking`，本阶段不做。

验收：`data/projects/*/agent/runs/` 中 step 含 reasoning 字段；`sessions/{sid}.json` 的消息内容无思考文本。

### A4. 前端 SSE 层透传（P0，依赖 A2）✅ 260922

- `api/generate.js` 的 `handleData` 增加 `thinking` 类型分支：直接 `onEvent?.({type:'thinking', text})` 透传，**不**累加进返回值 `content`。

验收：`useAgentGenerate` 的 `onEvent` 能收到 thinking 事件；`result.content` 不含思考文本。

### A5. 前端思考块 UI（P0，依赖 A4）✅ 260922

- `useAgentGenerate`：新增 `thinkingBuf` 累积；收到 thinking 事件时 `patchAssist({ thinking })`。阶段处理：THINKING 阶段收到 thinking 时保持 THINKING 不变（有内容可展示），首个 content delta 到达才切 STREAMING。
- 新组件 `component/chatpanel/ThinkingBlock.jsx`：
  - 收起态：一行「已深度思考」+ 展开箭头；展开态：灰字小号滚动区（max-height + overflow）。
  - 生成中实时展开（自动滚动到底），生成完成自动收起，用户手动展开则保持。
- 消息持久化形状：`thinking` 随消息对象存前端内存会话（`sessions.js` 存储层允许该字段透传即可，不参与 content 渲染）；历史消息无该字段则不渲染块。
- `AGENT_PHASE` 不新增枚举，复用现有 thinking/streaming 语义。

验收：推理模型点续写 → 黑盒等待期出现实时思考文本 → 正文开流后思考块收起；刷新后思考块不显示（本阶段）；切换非推理模型完全无感知。

## D. 工具决策轮流式化（P0~P1，依赖 A；下一阶段实施）

### D1. `model_client` 新增流式工具调用通道（P0，依赖 A1）⬜

- 新增 `chat_stream_tools(system, messages, tools, tool_choice, params)`（命名可议）：复用 `chat_stream` 的流式骨架，delta 同时产出 `reasoning` / `content` / `tool_call` / `done` 四类事件。
- 保留现有非流式 `chat()` 不动（摘要、router、连接测试仍用；也是回退路径）。
- 复用现成 `aggregate_tool_calls` 聚合分片 tool_calls；finish_reason 为 `length` 且聚合出空 tool_calls 时，视为「被截断未决」，按 `chat()` 现状语义返回空 content + 空 tool_calls（`generation_service` 已有空回退逻辑）。

验收：对同一 prompt，`chat_stream_tools` 聚合出的 tool_calls 与 `chat()` 结果等价（同模型同温度下人工比对多轮）。

### D2. 工具循环接入流式（P0，依赖 D1、A2）⬜

- `iter_generate` 的 `while True` 工具循环改调 `chat_stream_tools`：
  - reasoning delta → 立即发 `{"type":"thinking","phase":"tool_round"}` 帧（前端无需区分也行，后端可加 phase 标记便于 viewer 分段）；
  - 流结束后用聚合结果替换原 `assistant` 变量，后续执行逻辑**不变**（execute_tool、append messages、tool_progress、MAX_TOOL_ROUNDS 兜底全复用）。
- `run_store` 的 `agent_tool` step 增加 `reasoning` 字段（该轮思考原文），viewer 展示「决策轮思考」。
- **⚠️ 调研新增硬约束（260921）——决策轮的 `reasoning_content` 必须随 assistant 消息回传**：
  - DeepSeek V4 thinking mode 官方文档明示：携带 `tools` 的请求若不把 `reasoning_content` 完整回传，**API 直接 400**；
  - Qwen 官方 FAQ：function calling 时不回传 reasoning_content 会**降低准确性**（不报错）；
  - Kimi：单次任务的工具循环内要保留全部 reasoning 回传。
  - 现状 `generation_service.py:425` append 的 assistant 消息只有 `content` + `tool_calls`，**思考被丢弃**——这可能正是工具链路偶发异常的隐患之一（deepseek-v4-flash 默认开思考）。D2 落地时把该轮聚合到的 `reasoning_content` 一并放入回传的 assistant 消息（`{"role":"assistant","content":...,"reasoning_content":...,"tool_calls":[...]}`）；本轮被 1024 max_tokens 截断时回传已有的部分即可。
  - 会话历史持久化**仍不存** reasoning（原则 0.3-1 不变）——回传只发生在**同一次 turn 的工具循环内存消息**里，跨 turn 不保留（DeepSeek/Kimi/Qwen 均接受该做法；Qwen 的 `preserve_thinking` 是可选开关，本项目不开）。

验收：点续写后，**第一段可见输出从正文开流提前到工具轮思考开始**；`tool_progress`、轮次上限、`tool_answer` 兜底行为与现状一致；deepseek-v4-flash 连续多轮工具调用不再出现 400。

### D3. 降级与容错（P1，依赖 D2）⬜

- 流式通道抛 `ModelClientError` 时回退一次非流式 `chat()`（覆盖个别网关对 stream+tools 组合不支持的情况），不改变现有 `_tools_supported_error` 去 tools 退化路径。
- 连接中断（流中途断）已收到的 reasoning 仍透出，已聚合完整的 tool_calls 可继续执行；无法完成则走现有异常路径。

验收：人为模拟网关拒绝 stream+tools，功能退化为非流式工具轮 + 正常完成生成。

## B. Prompt 级 `<plan>` 结构化分析段（P1，D 完成后实施）

> 与 A/D 的区别：A/D 是把模型**自发**的思考接回来（仅推理模型受益）；B 是让**任何**模型在正文前输出一段可见的创作分析（段落承接、视角、节拍、伏笔），对生成质量有真实收益。

### B1. 提示词与契约（P1，依赖 D 验收）⬜

- `backend/app/prompts/` 新增 plan 指令块（拼入 `AGENT_SYSTEM` 或 `preset_intent` 之后）：
  - 仅 `DRAFT_PRESETS`（续写/润色/扩写）与确认属于写作的自由文本路径注入；闲聊、生成设定不注入。
  - 契约：正文前输出 `<plan>`（≤100 字，含：本段目标 / 承接点 / 视角节奏 / 需埋或回收的伏笔），`</plan>` 后直接正文，plan 内不得出现正文内容。
- 配置 `data/config.json` 增加 `plan_mode`（`auto` \| `on` \| `off`）和 `reasoning_models` 列表；不使用一个布尔值承载“普通模型默认开启、推理模型默认关闭、强制覆盖”三种语义。

验收：无开关回归 = 行为同现状；开启后各预设均输出 plan 段且正文干净。

### B2. 后端流式剥离（P1，依赖 B1）⬜

- 最终流式循环内做**状态机剥离**：进入 `<plan>` 后的 delta 归为 thinking（发 `{"type":"thinking","source":"plan"}` 帧），`</plan>` 之后恢复 content；plan 段不进 `parts`。
- 容错：
  - 流结束仍未闭合 `</plan>` → 全部按 plan 剥离，若剥离后正文为空则**降级为不过滤**（整段当正文，避免吞掉没遵守格式的输出）；
  - 未检测到 `<plan>` 开头 → 纯 content，零影响。

验收：正常输出正文无 plan 残留；畸形输出（无闭合/无 plan）不丢正文。

### B3. 判定链路对齐（P1，依赖 B2）⬜

- 确认 `_decide_draft`、`_resolve_content_anchor`、`DRAFT_PROSE_MIN_CHARS`、前端 `countWords` 全部基于**剥离后**正文（B2 已保证不进 parts，验收时专项检查闲聊误判 draft 的边界用例）。
- plan 文本随 run_store step `extra={"plan": ...}` 落盘。

### B4. 前端展示（P1，依赖 B2/A5）⬜

- thinking 事件带 `source: "plan"` 时渲染进与 A5 相同的折叠块，标题区分：「创作思路」（plan）vs「深度思考」（原生 reasoning），两者可共存于同一条消息。
- plan 来源的思考块在正文完成后**默认保持收起**。

### B5. 与推理模型的互斥（P1，依赖 B1；D 验收后实施）⬜

#### B5.1 启用决策

- `plan_mode=off`：任何模型都不注入 plan。
- `plan_mode=on`：符合写作路径时强制注入 plan，即使模型被识别为推理模型。
- `plan_mode=auto`：普通模型注入；命中 `reasoning_models` 的模型不注入，因为原生 reasoning 已提供过程信息，继续生成 plan 会重复消耗 token。
- 判定使用最终生效的模型名：请求体 `GenerateRequest.model` 优先于保存配置中的默认模型；模型名做大小写归一化后与 `reasoning_models` 中的完整名称或显式别名匹配。
- 未配置能力元数据的模型按普通模型处理，不使用宽泛的 `reason`、`think` 等模糊关键词自动判定；需要时将供应商别名加入 `reasoning_models`。

#### B5.2 Prompt 分层

- Router 和 `agent_tool` 决策轮使用不含 `<plan>` 的 system，避免工具决策轮产生无法撤回或无法正确剥离的 plan。
- 最终 `chat_stream` 单独使用 `final_system`：显式/Router 选中 `DRAFT_PRESETS` 时注入；自由文本只有在确认进入写作路径（例如读取前文工具后）才注入；闲聊和生成设定不注入。
- B 不修改 D 的工具调用协议，也不把 plan 指令放进跨轮工具回传的 assistant message。

#### B5.3 与 D 的关系

- D 阶段只透传模型原生 `reasoning`，不生成 `<plan>`，不改变普通模型最终 prompt。
- D 的流式工具调用与回退链路稳定后，B 才新增 `plan` source 和 `<plan>` 状态机。
- 推理模型在 `auto` 下只保留原生 reasoning；若用户确实希望看到可编辑的创作分析，可显式切换 `plan_mode=on`，接受额外 token 和双层思路展示。

## C. 独立「构思」调用 · 两段式（P2，远期）

> 本阶段只留设计边界，展开实现另立文档。

- **形态**：写正文前先发一次轻量非流式调用产出**节拍表**（structured：场景目标/情拍/收束点），流式或一次性展示；确认（或自动）后作为上下文注入正文生成。
- **增量价值**（相对 B）：节拍表可持久化、可复用、可编辑；能支撑「先出节拍 → 用户确认/改 → 再写」的确认式交互，是产品级差异化。
- **代价**：多一次完整往返延迟；节拍需二次注入；链路复杂度上升。
- **前置条件**：A/B/D 上线后通过 Agent Viewer 数据确认两点——①用户确实展开看思考；②plan/节拍类输出对草稿采纳率有可观测提升。
- **不做**：本阶段不落任何代码。
